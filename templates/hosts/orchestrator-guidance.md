# OMC repository orchestration

This repository uses OMC's shared workflow controller. The native Claude Code or Codex session is the lead interface; provider and model bindings for implementers and reviewers remain independent.

- Read `.omc/orchestrator.json` and run `omc orchestrator status` before starting or resuming orchestration work.
- Routing: at the start of every lead session and before workflow init or review, read `.omc/routing.md` if present. Treat its role, model, effort and executable choices as overridable defaults; verify availability, record actual model, effort, executable/CLI version and reason for any fallback in workflow evidence, and keep OMC review gates explicit.
- Use `omc team workflow` commands for workflow mutations. For worker publication, exclusively create `publication.helperResult.path` in the worker worktree, then execute `publication.publishInvocation.command` with `publication.publishInvocation.args` as an argument array. A shell-only worker may run a non-null `publication.publishCommand` unchanged; never interpolate paths into it, and stop if it is null.
- Failed packet: when checks fail or work exceeds scope, require a published `outcome: "failed"` handoff with available evidence. Inspect and reject the packet; to reuse its commit, create a follow-up workflow at the current integration head with corrected scope and declared checks, then accept and verify the new task. See `docs/WORKFLOW-V1.4.md` for the recovery steps.
- Shared append-only files: keep parallel packets' write scopes disjoint. Give one dependent integration task sole ownership of the shared file; after accepting its packet dependencies, append all entries there and run the cross-check.
- Switch leads only at a quiescent checkpoint with `omc orchestrator use` or `omc orchestrator handoff`. A host switch starts a fresh native session and keeps the shared OMC checkpoint.
- During a live workflow `run` or `resume`, only assigned task-branch commits may change Git refs in the leader checkout or its linked worktrees. They share refs: an unrelated fetch, branch, tag, or push can fail every candidate's protected-ref audit. Use an independent clone for separate Git work; inspect the audit artifact before attributing a ref change to a worker.
- Treat the OMC CLI operation gate and lease as authoritative. Native lifecycle hooks provide session checks and context; they do not replace core mutation gates.
- `omc team workflow run`, `resume`, `verify` and `review` drive providers and can take as long as the workflow's provider timeout. Give each call at least that long (a Claude Code Bash `timeout` up to the launch-provided maximum, or a yielding `exec` with polling in Codex); never background, kill or retry them. After a dead lead and provider are confirmed exited and their artifacts inspected, run `omc orchestrator recover --checkpoint <kind>` from a plain shell, then settle the attempt with `omc team workflow reject <name> <task> --reason <text>` before starting a new lead.
- Follow the hook guidance from `omc doctor hosts`: supported Codex versions require project trust and definition review with `/hooks`; unsupported versions need an upgrade. Diagnostics never approve hooks or establish native trust.
- Keep provider identity explicit. Preserve exact model identifiers, including `glm-5.3`, `glm-5.3-flash`, and `glm-5.3-flash[1m]`; do not infer a provider from a model-name substring.
- Do not run an OMX writer against `.omc` workflows or guess a migration between OMX and OMC state. Finish live OMX work in OMX before adopting this controller.
- Use the installed `omc-orchestration` skill and native role agents for operating details. Run `omc doctor hosts` when host assets, hooks, MCP, or CLI availability are uncertain.
